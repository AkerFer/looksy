# Архитектура Looksy — этапы 1–6

Модульный монолит Django 5.2 + DRF. Отдельные веб- и Flutter-клиенты используют `/api/`.
PostgreSQL 17 — основная БД (Compose), SQLite — явный резерв для локальных тестов. Перед публикацией: отдельное хранилище
приватных фотографий, HTTPS reverse proxy и production WSGI-сервер.
Их конфигурация и проверка относятся к этапу 8; текущий runserver не production.

## Схема

- User → UserProfile и OutfitPreference: 1:1, CASCADE.
- OutfitCalendarEntry → User/Outfit: N:1, CASCADE, уникальная пара user/date.
- User → ClothingItem, Outfit, OutfitFeedback, SavedOutfit, WeatherContext: 1:N, CASCADE.
- ClothingCategory → ClothingItem: 1:N, PROTECT; цвета — M:N.
- Outfit ↔ ClothingItem: M:N через OutfitItem; пара уникальна.
- OutfitFeedback и SavedOutfit: уникальная пара пользователь/образ.
- Rating: 1–5 (API и CHECK БД); координаты: диапазоны API и CHECK БД.
- Индексы пользователь/дата на пользовательских коллекциях; FK и уникальные поля
  дополнительно индексируются Django/БД.

Категории и цвета — общий справочник, доступный только для чтения через API.
Начальная миграция справочника не создаёт фиктивный гардероб или пользователей.
WeatherContext доступен только для чтения; запись из погодного сервиса — этап 5.

## Границы безопасности

Queryset каждого пользовательского ресурса фильтруется по request.user. Владелец
назначается сервером и отсутствует в записываемых полях. Связанные items/outfit
выбираются только среди объектов текущего пользователя. Чужой ID: 404 для ресурса,
400 для связи. OutfitItem управляется только через Outfit API, отдельной записи нет.
Эта граница проверяется на уровне REST API; прямой SQL/ORM — доверенный внутренний
интерфейс, который не должен принимать непроверенные идентификаторы.

JWT SimpleJWT с ротацией и blacklist refresh-токенов, а также сессионная аутентификация Django, хеширование паролей Django, password validators,
CSRF для регистрации, входа, выхода и изменения данных. Cookies HttpOnly/SameSite,
Secure и HTTPS redirect при DEBUG=false. In-memory throttling — базовая защита;
перед публикацией нужны общий cache и ограничения входа на reverse proxy.
Секрет в .env, локальный файл исключён из Git. Production должен использовать
секрет окружения и явный список hosts, без testserver.

DELETE account требует текущий пароль, удаляет связанные записи транзакционно.
PrivatePhoto привязан ровно к одной вещи или профилю (CHECK). Файлы удаляются
после коммита при замене/удалении фото, вещи или аккаунта. Публичной раздачи
MEDIA_ROOT нет. Загрузка, валидация и приватная выдача реализованы; подробности
и ограничения распознавания: [этап 3](stage-3.md).
Погодный клиент и AI-стилист реализованы с резервным режимом; живые сервисы пока не проверены из-за сетевых ограничений и отсутствия Ollama. Сегментация работает локально,
для распознавания категорий реализован ONNX-адаптер без установленных весов.
