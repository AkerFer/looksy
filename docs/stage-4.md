# Этап 4 — генератор образов

Детерминированный Python-алгоритм работает локально, без LLM и платных API.
Каждый результат ссылается только на существующие вещи текущего пользователя.
Автоматическая погода добавлена на [этапе 5](stage-5.md); свободный текст обсуждается в отдельном AI-чате, а не заменяет ограничения генератора; интерфейс
и flat-lay из приватных фотографий — этап 6. В API уже есть item_details с
настоящими URL фотографий (с авторизацией), без сгенерированных предметов.

## Запуск

```bash
cd /workspace/looksy
docker compose up -d --wait db
cd backend
../.venv/bin/python manage.py migrate
../.venv/bin/python manage.py test
../.venv/bin/python manage.py runserver 127.0.0.1:8000
```

Новых пакетов относительно этапа 3 нет. Миграция 0006 добавляет comfort/warmth
вещей и JSON оценки/контекста генерации образа. Для существующих вещей значения
не выдумываются: comfort/warmth изначально null.

## Характеристики вещей

PATCH `/api/clothing/<id>/`: comfort и warmth — nullable целые 1…5.
comfort: субъективный комфорт вещи, от низкого к высокому. warmth: от лёгкой до
очень тёплой. Значения сохраняются вручную; 0 и 6 отвергаются API и CHECK БД.
Стили, сезон, цвета, крой и доступность используются из сохранённого гардероба.
Материал не участвует в оценке: надёжных данных о свойствах ткани пока нет.

## Генерация

POST `/api/outfits/generate/` (JWT или сессия с CSRF), например:

```json
{
  "count": 3,
  "occasion": "university",
  "style": "minimalism",
  "comfort_priority": 75,
  "season": "autumn",
  "temperature_c": 14,
  "required_items": [12],
  "excluded_items": [19],
  "preferred_colors": [1],
  "notes": "Свободные пожелания для будущей AI-интеграции"
}
```

ID заменяются на реальные свои ID и ID общего справочника цветов.
Все параметры необязательны. count: 3…5, по умолчанию 3; occasion: everyday,
university, work, sport, party, formal (по умолчанию everyday).
season: all/summer/winter/spring/autumn; all не ограничивает сезон, конкретный
сезон допускает вещи этого сезона и all. Температура — конечное число -60…60 °C,
вводится вручную, не выдаётся за прогноз. comfort_priority — 0…100.

Тексты стилей сравниваются без учёта регистра, но без семантического перевода:
`minimalism` и `минимализм` — разные метки. Сначала используется style запроса,
затем styles/style настроек, затем preferred_style профиля; если пусто, простая
таблица occasion → стили: university → casual/minimalism, work → business/smart
casual, sport → sport/athleisure, formal → formal/business, party → party,
everyday → casual. Это эвристика, а не автоматическое понимание мероприятия.

Предпочтительные цвета запроса заменяют список из настроек (пустой список его
отключает). Нежелательные цвета и preferred_fit берутся из настроек.
Приоритет комфорта берётся из запроса, иначе из настроек (обычно 50).
notes сохраняется, но не влияет на выбор. Ответ явно предупреждает об этом:
строгие пожелания нужно выразить required_items/excluded_items/season.

### Обязательные ограничения перед оценкой

- Только свой гардероб, is_available=true.
- Исключаются excluded_items и excluded_categories из настроек.
- required_items должны остаться после ограничений; противоречие → 400.
- Не более одной вещи на слот. «Другие» нельзя сделать обязательными — нужно
  вручную уточнить категорию. Несовместимые обязательные слоты → 400.
- Полный комплект: top + bottom + shoes либо dress + shoes.
- Не более одного outerwear и одного accessory. Платье не совмещается с
  верхом/низом. Oversized верх/платье не надевается под slim outerwear.
- При эффективной температуре ≤10 °C обязателен внешний слой. Эффективная
  температура = ручная + 2×(heat_sensitivity−3) − 2×(cold_sensitivity−3).
  Это условная эвристика комфорта, не медицинская/погодная гарантия.

Чужой, удалённый и несуществующий ID возвращают одинаковую ошибку 400.
Нежелательный цвет — мягкое предпочтение с предупреждением при использовании.
Для абсолютного запрета используйте excluded_items либо excluded_categories.

### Оценка

Начальные веса: comfort 35, weather 25, style 20, colors 15, preferences 5.
По умолчанию comfort_priority меняет вес comfort от 20 до 50 (при 50 — 35);
остальные веса пропорционально занимают остаток. Можно полностью заменить веса:

```json
{
  "weights": {
    "comfort": 35,
    "weather": 25,
    "style": 20,
    "colors": 15,
    "preferences": 5
  }
}
```

Нужны все пять целых неотрицательных весов с суммой 100. Явные weights имеют
приоритет над comfort_priority. Без температуры weather=null, его вес обнуляется,
остальные нормализуются до 100. Запрос только с weather=100 без температуры
отклоняется, а не получает фиктивную оценку.

| Критерий | Эвристика 0…100 |
| --- | --- |
| comfort | Среднее пользовательских comfort (1 → 0, 5 → 100); неизвестные → 50 |
| weather | Близость warmth к целевому 1/2/3/4/5 при температуре ≥25/≥18/≥10/≥0/<0; неизвестные → 50; обувь/аксессуары не учитываются |
| style | Совпадение хотя бы одной метки → 100, известные несовпадающие → 25, неизвестные → 50 |
| colors | Среднее по парам HEX в HSV: нейтральная пара → 100, близкие/противоположные оттенки → 90, прочие → 55; один цвет → 80, нет данных → 50 |
| preferences | Совпадение предпочитаемого цвета, штраф за нежелательный и совпадение preferred_fit; при отсутствии настроек → 50 |

Итог — взвешенное среднее. В ответе есть отдельные критерии, фактические веса,
объяснение, предупреждения о неизвестных характеристиках и источник температуры.
Рейтинг субъективен, не является объективной оценкой стиля. Слои учитываются
структурно; реальная суммарная теплоизоляция тканей и защита от ветра/дождя
не моделируются.

### Ограниченный поиск

До 500 вещей в гардеробе, иначе 400 без молчаливого усечения списка. Beam search
оставляет 48 лучших частичных комплектов после каждого слота. Противоречивые
слои отбрасываются до оценки. Результаты уникальны по множеству ID и сортируются
по score, затем ID для стабильного порядка. search.pruned=true означает,
что поиск был сокращён: глобально лучшие комбинации не гарантируются.

Если нашлось меньше count, возвращаются все найденные без дублирования.
Если комплектов нет, ответ 200 с пустым results и понятной причиной; вещи и
результаты не выдумываются. Повторение одинакового запроса при неизменных данных
даёт тот же порядок. Чтобы изменить подбор, задайте другие ограничения/стиль/
веса; случайной кнопки «новый вариант» пока нет.

## Ответ, история и избранное

При наличии результатов — 201; каждый результат сразу записан в Outfit/OutfitItem.
Это история: повторный запрос создаёт новые записи, даже при том же составе.
Все варианты одного запроса сохраняются транзакционно; выбранные вещи блокируются
до коммита, чтобы обновления не изменили их в середине генерации.

Корень ответа: count, requested_count, messages, weights, search, results.
Каждый результат: id, name, items (ID), item_details (карточки), created_at,
generation (score/criteria/weights/explanation/warnings/request/item_versions),
generation_is_stale.

GET `/api/outfits/` и `/api/outfits/<id>/` — своя история.
POST `/api/saved-outfits/` с `{ "outfit": <id> }` — добавить в избранное.
DELETE `/api/saved-outfits/<saved-id>/` — убрать из избранного, не удаляя образ.

generation — только для чтения, это историческая оценка в момент генерации.
После изменения/удаления вещи generation_is_stale=true; клиент должен скрывать
актуальный рейтинг или подписывать его как устаревший. Изменение списка items
через PATCH образа сбрасывает generation. Изменение настроек не пересчитывает
прошлые результаты; для новых настроек нужно запустить новую генерацию.
Прямые SQL/bulk update без updated_at обходят проверку версий: это доверенный
внутренний интерфейс, не пользовательское API.

## Проверки

```bash
cd /workspace/looksy/backend
../.venv/bin/python manage.py test wardrobe.test_generator
../.venv/bin/python scripts/smoke_generator.py http://127.0.0.1:8000
```

Smoke создаёт временный аккаунт и настоящий тестовый гардероб в БД, проверяет
подбор, обязательные/исключённые вещи, историю, избранное и устаревание оценки,
затем удаляет аккаунт и связанные данные. Эти тестовые вещи не появляются
в пользовательских гардеробах и не служат подменой backend.

Проверено: 63 теста на PostgreSQL, 23 теста генератора на SQLite; миграция
0006 применена в обеих БД. HTTP smoke прошёл, временный аккаунт удалён.
Django check и проверка отсутствия несозданных миграций прошли.
