# Этап 5 — Open-Meteo и AI-стилист

Клиенты погоды и Ollama реализованы. Подбор без сервисов остаётся работоспособным:
не используются фиктивные прогнозы, ответы модели или выдуманные вещи.
В текущей облачной среде живые сервисы **не подтверждены**: Open-Meteo возвращает
403 на CONNECT сетевого прокси, Ollama не запущена и моделей нет; registry.ollama.ai
также заблокирован (403). Успешные ответы проверяются контрактными тестами с
подменой транспорта, отказ и резервный режим — настоящими HTTP-запросами.

## Запуск backend

```bash
cd /workspace/looksy
docker compose up -d --wait db
cd backend
../.venv/bin/python manage.py migrate
../.venv/bin/python manage.py runserver 127.0.0.1:8000
```

Новых Python-зависимостей относительно этапа 3 нет (requests уже закреплён).
Миграция 0007 добавляет координаты профиля и поля погодного контекста.

## Настройка сети

Для живой погоды в настройках облачной среды нужно **добавить** разрешения,
сохранив существующие домены:

- api.open-meteo.com
- geocoding-api.open-meteo.com

Не требуются API-ключи. Запрос явно отправляет выбранные координаты (либо название
города в поиске) провайдеру Open-Meteo. Учитывайте условия бесплатного Open-Meteo
API: для публичного коммерческого использования отдельно проверьте лицензию,
атрибуцию и тарифные ограничения. Ответ включает source для отображения источника.

Для необязательной локальной LLM нужно скачать Ollama и веса. Docker Registry
использует уже разрешённые домены пакетов. Загрузка весов требует как минимум
registry.ollama.ai; при перенаправлении на CDN потребуется разрешение фактического
CDN из ошибки загрузки. Список CDN здесь не угадывается. Во время реализации
редактор черновика среды дважды вернул ошибку чтения, поэтому сетевые настройки
не изменены и сохранение этих разрешений не подтверждено.

## Город и координаты

GET `/api/locations/?search=Ташкент` возвращает до пяти кандидатов:
name, region, country, latitude, longitude, timezone. Это поиск, а не
автоматический выбор первого совпадения. Пользователь выбирает кандидата.
Поиск требует авторизации. Пустой ответ — results=[], сбой — 503 с сообщением.

Сохранение выбора:

```http
PATCH /api/profile/
```

```json
{"city":"Ташкент","latitude":"41.31108","longitude":"69.24056"}
```

Можно указать координаты вручную без геолокации. Оба значения обязательны вместе
(или оба null). При смене city без новых координат старые координаты очищаются,
чтобы не запрашивать погоду прежнего города. Одного названия города недостаточно
для автоматического прогноза: неоднозначное геокодирование не делается скрыто.

## Прогноз

POST `/api/weather/forecast/`:

```json
{
  "latitude":"41.31108",
  "longitude":"69.24056",
  "at":"2026-11-12T09:00:00+05:00"
}
```

at необязателен (текущее время); при указании обязателен часовой пояс.
Допускается время от предыдущего часа до шести дней вперёд. Пример даты нужно
заменить актуальной. Open-Meteo запрашивается в UTC; выбирается ближайший
доступный час в указанных UTC-сутках (отклонение не больше часа).

Ответ: id, temperature_c, apparent_temperature_c, precipitation_probability,
wind_speed_kmh, condition (код WMO), forecast_for (час прогноза), observed_at
(время получения, не фактическое наблюдение), source=open-meteo, cached,
latitude/longitude. Не путайте время получения с временем прогноза.

Публичные прогнозы кэшируются на 10 минут по координатам/UTC-дате. Профиль,
гардероб и авторизация в общий кэш не попадают. Успешный выбранный контекст
сохраняется только для текущего пользователя; GET `/api/weather/` — его история.
Ошибка не записывает выдуманную погоду, возвращает 503. Удаление аккаунта удаляет
профиль и погодную историю. В production потребуется политика срока хранения
географической истории.

## Погода в генераторе

POST `/api/outfits/generate/` дополнительно принимает:

```json
{
  "use_weather":true,
  "weather_location":{"latitude":"41.31108","longitude":"69.24056"},
  "forecast_at":"2026-11-12T09:00:00+05:00",
  "weather_failure":"continue"
}
```

use_weather по умолчанию false: без согласия в запросе внешнего обращения нет.
weather_location необязателен: иначе используются выбранные координаты профиля.
forecast_at необязателен. Одновременное use_weather=true и temperature_c → 400.
Ручная температура из этапа 4 продолжает работать без сети.

Генератор использует apparent_temperature_c и чувствительность профиля. При
экстремальном apparent значении за пределами -60…60 оно ограничивается этим
диапазоном только для рейтинга; исходный прогноз сохраняется без такой подмены.
При осадках ≥60% или ветре ≥30 км/ч внешний слой получает +10 к погодной оценке,
его отсутствие — −15 (оценка остаётся в 0…100). Это эвристика, не проверка
водостойкости: ответ предупреждает, что защита ткани от дождя/ветра неизвестна.
Все обязательные ограничения проверяются до выбора образа, погодный бонус
не может вернуть исключённую вещь.

weather_failure=continue (по умолчанию): при сбое/невыбранном городе генерация
идёт без погоды, её вес отключается/перераспределяется; возвращаются явные
weather_status=unavailable, weather=null и сообщение. abort: 503 без сохранённых
образов. При успехе weather_status=ok, weather содержит источник/время/ID контекста,
а снимок прогноза сохраняется в generation.weather каждого образа. Без запроса
погоды weather_status=not_requested. Прогноз получается **до** блокировок вещей
в БД; сетевое ожидание не удерживает транзакцию генератора.

## AI-стилист

POST `/api/stylist/`:

```json
{"message":"С чем сочетать мои брюки?","use_ai":true,"weather_context_id":123}
```

message обязателен (до 1000 символов), use_ai=true по умолчанию; false отключает
обращение к модели. weather_context_id необязателен: можно передать только свой
ранее полученный контекст (чужой → 404). Это явно выбранный снимок, он не
обновляется автоматически; для нового времени сначала получите свежий прогноз.
Чат пока без долговременной истории и инструментов выполнения действий.

Ollama получает только доступные вещи текущего пользователя без исключённых
категорий: имена/ID/метки/крой/HEX, предпочтения, выбранный погодный снимок и
сообщение. Фото, токены и пароли модели не передаются. Ограничение контекста:
не больше первых 100 вещей и 12 КБ JSON инвентаря; при усечении есть предупреждение
и context_count. Ollama разрешена только на loopback HTTP, redirects запрещены;
пользовательский запрос не может задать адрес сервиса. Локальная Ollama не должна
публиковаться без аутентификации в интернет.

Модель возвращает структурированный JSON. Сервер проверяет типы, длины и каждый
item_id: неизвестный/чужой/недоступный/непереданный модели ID вызывает резервный
ответ. Карточки в items всегда берутся из настоящей БД. missing_slots — отдельные
предложения о недостающих категориях; они **не создают** вещи. Ответ source=ollama
содержит предупреждение: свободный текст модели может ошибаться. Семантически
проверить все фразы модели невозможно; текст не считается фактом об инвентаре
и должен отображаться как обычный текст, без исполнения HTML/команд.

Если модель отсутствует, отвечает неверно или превышает таймаут — source=rules.
Локальный генератор предлагает базовый комплект и отдельные недостающие слоты;
свободный текст не интерпретируется, о чём ответ сообщает. При weather_context_id
резервный подбор использует выбранный снимок. Ни AI, ни fallback не меняют
гардероб и не сохраняют образ: для сохранения используются обычные endpoints.
Чат не меняет обязательные ограничения/веса генератора через свободный текст.

### Необязательная Ollama

Конфигурация Compose содержит профиль ai (проверена синтаксически; запуск
контейнера и загрузка весов в этой среде не проверены):

```bash
cd /workspace/looksy
docker compose --profile ai up -d ollama
docker compose exec ollama ollama pull qwen2.5:0.5b
```

Можно вместо Docker использовать уже установленную локальную Ollama.
В .env: OLLAMA_URL=http://127.0.0.1:11434, OLLAMA_MODEL=qwen2.5:0.5b,
OLLAMA_TIMEOUT=30. У Docker 4 ГБ RAM и 2 CPU, данные модели хранятся в volume.
Хостовый CA bundle монтируется для проверяемого TLS при загрузке моделей.
При локальном запуске на другой ОС адаптируйте путь CA bundle. Образ latest —
конфигурация разработки; перед публикацией нужно закрепить проверенный digest.
Качество маленькой модели и советы не проверены на реальном гардеробе.

## Надёжность и тесты

HTTP: connect timeout 3s, read timeout 8s для погоды/30s для Ollama. Погода
повторяется один раз при timeout/connection error/5xx; 403/429 и redirects не
повторяются. Ошибочные или слишком большие ответы отклоняются: максимум
512 КБ погоды, 64 КБ AI. Проверки конечности/диапазонов, длины массивов и
схемы не дают записать некорректный прогноз. TLS-проверки и унаследованный прокси
не отключаются. У Ollama нет повтора, чтобы не удваивать длительный инференс.
Таймаут чтения не является общим дедлайном запроса; очередь/глобальные лимиты
инференса остаются задачей этапа 8. Общий throttling Django уже применяется.

```bash
cd /workspace/looksy/backend
../.venv/bin/python manage.py test
../.venv/bin/python scripts/smoke_services.py http://127.0.0.1:8000
# Требует реально доступных Open-Meteo и Ollama, иначе завершится ошибкой:
../.venv/bin/python scripts/smoke_services.py http://127.0.0.1:8000 --require-live
```

Обычный smoke проверяет и честно печатает состояние сервисов, включая
UNAVAILABLE; это не доказательство успешного живого прогноза/инференса.
Он создаёт и удаляет временный настоящий аккаунт, тестовые вещи и историю.

Проверено в текущей среде: 88 тестов на PostgreSQL, 25 тестов сервисов на SQLite;
миграция 0007 применена в обеих БД. Успешные прогнозы/AI-ответы проверены
подменой транспорта. Реальный HTTP smoke подтвердил 503 погодного провайдера,
подбор без погоды и AI fallback; временный аккаунт удалён. Живой успешный
прогноз и инференс Ollama не подтверждены. Django check, проверка миграций
и синтаксическая проверка Compose прошли.
